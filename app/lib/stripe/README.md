# app/lib/stripe/ — integracja płatności Stripe

Moduły obsługujące płatności przez Stripe Connect (Express). Trener łączy własne
konto Stripe, podopieczni płacą za współpracę. Integracja opcjonalna — aplikacja
działa bez niej (`stripeConfigured()`).

## Pliki

| Plik | Rola / kluczowe eksporty |
|---|---|
| `client.ts` | Leniwy klient platformy Stripe: `getStripe()` (rzuca, gdy brak `STRIPE_SECRET_KEY`), stała `STRIPE_API_VERSION` (przypięta do wersji typów zainstalowanego SDK — `2026-05-27.dahlia`). |
| `connections.ts` | Repo tabeli `stripe_connections`: `getConnectionStatus` (bezpieczny do loadera, bez sekretów), `getConnectionRow` (pełny wiersz do orkiestracji), `ensureExpressAccount` (idempotentnie tworzy konto Express + zapisuje wiersz, zwraca `accountId`; `accounts.create` z `idempotencyKey` per trener — retry po nieudanym insercie zwraca to samo konto, brak sierot), `createOnboardingLink` (jednorazowy link onboardingu, `account_onboarding`), `applyAccountUpdate` (aktualizuje flagi `charges/payouts/details` po `stripe_account_id` — używane przez webhook). Tenant-scope: `trainerId`. |
| `status.ts` | Czysty mapper statusów: `SubscriptionStatus` (lustro Stripe + `none` + `paused`), `mapStripeStatus`, prezentacja UI subskrypcji (`subscriptionPresentation` → `StatusPresentation`, etykieta + tone; `paused` → „Wstrzymana"), oraz `invoiceStatusLabel` (status faktury/płatności → polska etykieta, nieznane przechodzą bez zmian). Bez I/O. |
| `access.ts` | Czysty predykat dostępu podopiecznego (bez I/O): `ACCESS_STATUSES` (statusy wpuszczające: `active`/`paused`/`past_due` — grace), `paymentRequired` (gating ma sens tylko gdy Stripe skonfigurowany + trener ma `chargesEnabled` + jest cena), `hasAppAccess` (gdy płatność niewymagana → zawsze dostęp; wymagana → tylko status z `ACCESS_STATUSES`). Używany w gatingu layoutu podopiecznego (`app/routes/podopieczny/_layout.tsx`). |
| `subscriptions.ts` | Repo `coaching_subscriptions` + orkiestracja Billing/Checkout (tenant-scope `trainerId`/`traineeId`): `getSubscriptionForPair`, `setMonthlyAmount` (tworzy nowy Price z nazwą produktu „Prowadzenie treningowe — {imię trenera}" + upsert wiersza pary; podmiana itemu aktywnej subskrypcji), `ensureCustomer`, `createCheckoutSession` (mode `subscription`, destination charges → konto trenera, `application_fee_percent` 0), `createPortalSession` (Customer Portal), `cancelSubscription`, `pauseSubscription`/`resumeSubscription` (Stripe `pause_collection` z `behavior: "void"` / czyszczenie pustą wartością; status `paused`/`active` po naszej stronie — `pause_collection` NIE zmienia `subscription.status`), `applySubscriptionUpdate` (setter dla webhooka; `paused: true` nadpisuje status na `paused`), `linkCheckoutResult`; `cleanupSubscriptionForTrainee` (best-effort przy usuwaniu podopiecznego: `subscriptions.cancel` + `customers.del` — stop billing + RODO; no-op gdy Stripe nieskonfigurowany; wołane z trasy PRZED kaskadą DB); klasa błędu `SubscriptionError` (komunikaty PL). `customers.create` z `idempotencyKey` (per para) — brak duplikatu klienta przy retry (`prices.create` bez klucza: nazwa produktu zależy od zmiennej nazwy trenera, duplikat Price nieszkodliwy). Wywołania Stripe poza transakcją DB. |
| `webhook.ts` | Obsługa webhooka Stripe: `verifyAndParse` (weryfikacja podpisu HMAC przez `constructEvent`; próbuje kolejno `STRIPE_WEBHOOK_SECRET` (konto) i `STRIPE_CONNECT_WEBHOOK_SECRET` (Connected accounts) — dwa destinations, dwa sekrety; rzuca przy braku sekretu/złym podpisie), `mapEvent` (CZYSTA funkcja: event → `Change` lub `null`; obsługuje `invoice.paid/payment_failed`, `customer.subscription.updated/deleted` (wykrywa też wstrzymanie — `paused: sub.pause_collection != null`, bo `pause_collection` nie zmienia `status`), `checkout.session.completed`, `account.updated`; faktura bez `id` → `null`), `applyChange` (dispatch do `recordInvoice`/`applySubscriptionUpdate`/`linkCheckoutResult`/`applyAccountUpdate`; idempotentny po `stripe_invoice_id`/`stripe_subscription_id`; invoice bez pary → loguje ostrzeżenie i pomija). Dodatkowo trasa `routes/webhooks.stripe.tsx` deduplikuje po `event.id` (tabela `processed_webhook_events`, insert-first/on-conflict-skip; przy błędzie `applyChange` marker jest cofany, by Stripe ponowił). **Ścieżki pól (stripe@22.2.0, `2026-05-27.dahlia`):** metadane pary na fakturze pod `parent.subscription_details.metadata`; `current_period_end` subskrypcji w `items.data[0].current_period_end`. |

> Repo historii płatności (`subscription_payments`) mieszka poza tym katalogiem — w
> [`../payments.ts`](../payments.ts) (`listPaymentsForPair`, `listPaymentsForTrainee`,
> `recordInvoice`), bo to czysty odczyt/zapis tabeli bez wywołań API Stripe.
